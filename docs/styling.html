Styling

The renderer ships no CSS. What it does ship is a contract: stable class names for structure, data-* attributes for state, and inline styles restricted to values that only exist at render time. Write CSS against those three tiers and the grid can change internally without breaking your sheet.

#The three tiers

Every attribute the grid emits belongs to exactly one of these tiers, and the tier tells you how stable it is and what you may do with it.

TierWhat it isGuarantee
dxg-<part> classes Structural identity — which part of the grid this element is. Stable and never state-dependent. Safe to target directly.
data-<state> attributes Live state — sorted, selected, pinned, dragging. Style via attribute selectors. Mirrors the ARIA the grid emits.
Inline style Geometry only: column widths, pinned-column offsets. Never colors, never spacing, never anything you would want to theme.

A copy-me reference stylesheet lives at examples/basic/assets/grid.css. It is a neutral, token-driven look — start from it and override, or delete it and write your own.

#Structural classes

Class names describe what an element is, not how it looks or what state it is in. A row is dxg-row whether or not it is selected; the selection lives in a data-* attribute. That separation is what lets you write one rule per part and one rule per state instead of a matrix of compound classes.

The set below is the part of the surface you will reach for most. It is not exhaustive — the renderer emits well over a hundred dxg-* names covering the calendar, the export menu, chips, the column menu and so on. Inspect the DOM or read the reference sheet for the rest.

#State attributes

Boolean states are present-or-absent, so test for the bare attribute. Enumerated states carry a value, so match on it. Never encode state in a class name of your own by, say, adding a selected class in a wrapper component — the grid already told you, and the attribute is what stays in sync with the ARIA.

The pattern is always the same: one selector per part, one selector per state on that part.

your-sheet.css
/* structure */
.dxg-row { border-bottom: 1px solid var(--line); }

/* state, layered on top */
.dxg-row:hover            { background: var(--hover); }
.dxg-row[data-selected]   { background: var(--selected); }

/* enum state matches on the value */
.dxg-cell[data-align="end"]    { text-align: end; }
.dxg-cell[data-align="center"] { text-align: center; }

/* the sort arrow is only visible once the column sorts */
.dxg-sort-indicator                    { opacity: 0; }
.dxg-header-cell[data-sorted="asc"]  .dxg-sort-indicator,
.dxg-header-cell[data-sorted="desc"] .dxg-sort-indicator { opacity: 1; }

/* hide the mobile-hidden columns at your own breakpoint, not the grid's */
@media (max-width: 640px) {
  .dxg-cell[data-hide-mobile] { display: none; }
}
The mobile breakpoint is yours. The grid does not decide when narrow is narrow. It only marks which columns the author flagged as droppable via data-hide-mobile; the media query that acts on it lives in your sheet.

#Why inline style is limited to geometry

Inline styles win the cascade, so anything the renderer puts there is something you cannot override without !important. That makes inline style a liability, and the rule is therefore narrow: the grid emits it only for values that cannot be expressed in a stylesheet because they are not known until render time.

In practice that is two things.

  • Column width. When a user drags a resize handle the resulting pixel width exists only in that session's state, so the header and body cells receive width, min-width and max-width inline. A column declared with .width("12rem") and never resized gets only a min-width.
  • Pinned-column offset. A pinned column's left is the sum of the widths of the columns pinned before it — a running total that depends on the live layout, so it is computed and emitted inline.

Everything else about a pinned cell — its background, its shadow, the divider that separates it from the scrolling columns — is yours, keyed off [data-pinned]. Likewise the keyboard focus ring is .dxg-cell[data-kbd-focus], not an inline outline. If you ever find a color or a padding value inline, that is a bug worth filing.

the grid emits geometry, you supply the look
/* the grid emitted: style="width:180px; min-width:180px; left:44px;" */
.dxg-cell[data-pinned] {
  position: sticky;              /* yours */
  z-index: 2;                     /* yours */
  background: var(--surface);   /* yours */
  box-shadow: 2px 0 0 var(--line);
}

#Theming with tokens

The reference stylesheet does not hardcode colors in its rules. Every value it uses comes from a --dxg-* custom property declared on :root, so reskinning the grid to match your app is a block of variable overrides rather than a rule-by-rule rewrite. The sheet also ships a prefers-color-scheme: dark block, so it is theme-aware with zero setup.

TokenControls
--dxg-bgThe grid's base background.
--dxg-surface, --dxg-surface-altRaised surfaces: popovers, menus, cards.
--dxg-header-bgThe sticky header background.
--dxg-text, --dxg-text-muted, --dxg-text-faintThe three text weights.
--dxg-borderEvery rule line and divider.
--dxg-accent, --dxg-accent-weakSort and selection accent, and its tint.
--dxg-row-hover, --dxg-row-selectedRow hover and selected backgrounds.
--dxg-radiusCorner rounding.
--dxg-cell-pad-y, --dxg-cell-pad-xCell padding — the density dial.
--dxg-fontThe grid's font stack.
reskinning without touching a rule
:root {
  --dxg-accent: #4f46e5;
  --dxg-accent-weak: #e0e7ff;
  --dxg-radius: 12px;
  --dxg-font: "Inter", system-ui, sans-serif;
}

/* a tighter grid is two tokens, not a density mode */
.dxg-root.compact {
  --dxg-cell-pad-y: 0.25rem;
  --dxg-cell-pad-x: 0.5rem;
}
GridDensity is not a CSS hook. The density prop chooses how much chrome the grid renders — Minimal drops the filter funnels, column chooser, group-by and the single-page footer. It changes which elements exist, not how they are spaced, and it emits no attribute on the root. Visual density is the padding tokens above.

#Accessibility, and why state is duplicated

The grid emits its own ARIA. The table carries role="grid" with aria-rowcount and aria-colcount; header cells are role="columnheader" with scope="col" and an aria-sort of ascending / descending / none; body cells are role="gridcell"; menus use role="menu" and role="menuitem"; toggles carry aria-pressed, popovers aria-expanded and aria-haspopup. Every icon-only control has an aria-label, including the selection checkboxes — "Select row" and "Select all rows on this page".

So sorted state exists twice on a header cell: as aria-sort="ascending" and as data-sorted="asc". That is deliberate. If styling read the ARIA attribute directly, the two concerns would be welded together and a future ARIA correction would break your CSS. Emitting both from the same computed value means they are generated side by side and cannot drift — the assistive tree and the stylesheet each get an attribute shaped for their own job.

The practical consequence: style from data-*, and leave the aria-* attributes alone. Do not select on them, and do not override them from the host.
