grid-state

The interaction controller. Where grid-core owns the data pipeline, this crate owns the state machine around it: the live query, the selection set, the view mode, and the intent methods a renderer calls when a user clicks something. No UI and no framework — just the transitions, so they are unit-testable and identical across renderers. #![forbid(unsafe_code)], 11 tests.

#The render loop

The contract is a cycle, and it is worth internalising because it explains why this crate holds no rows.

  1. A renderer holds a GridState.
  2. A user interacts; the renderer calls an intent method — toggle_sort, next_page, toggle_row.
  3. The renderer reads state.model() and re-queries its DataSource.
  4. It draws the returned ResultSet.

The state never touches your data. It describes what to ask for, which is why a change of sort column and a change of page look identical from the outside: mutate, re-query, redraw.

#ViewMode

List (row) versus card (gallery) presentation.

grid_state::ViewMode
pub enum ViewMode { List, Card }

impl ViewMode {
    pub fn is_card(self) -> bool;
}

is_card lives on ViewMode, not on GridState, so the idiomatic read is state.view().is_card(). It is Copy, so there is no borrow to juggle.

#GridState

Three private fields — the query model, a HashSet of selected ids, and the view mode. Private on purpose: every mutation goes through an intent method so the invariants below cannot be bypassed by a renderer setting a field directly.

grid_state::GridState
pub struct GridState { /* private */ }

impl GridState {
    // `default_card` picks the initial view; page_size is clamped to ≥ 1.
    pub fn new(page_size: usize, default_card: bool) -> Self;
}

Reads

MethodReturns
model()&QueryModel — pass to a DataSource to materialise rows.
search()&str — the current search text.
sort()Option<Sort> — a clone of the active sort.
page()usize — the zero-based page index.
page_size()usize — rows per page.
view()ViewMode.
sort_dir_for(key)Option<bool> — Some(true) ascending, Some(false) descending, None if this is not the sorted column.

sort_dir_for is the one a header cell wants. It answers "am I the sorted column, and which way" in a single call, so a renderer does not have to unwrap the Option<Sort> and compare keys per header.

Query intents

MethodEffect
set_search(q)Replace the search text. Resets to page 0.
clear_search()Empty the search text. Resets to page 0.
toggle_sort(key)Advance this column's tri-state sort. Resets to page 0.
set_view(view)Switch list ⇄ card. Does not touch the page or selection.

toggle_sort takes a &'static str, matching the ColumnDef key type, so no allocation happens on a header click.

Pagination intents

MethodEffect
set_page(page)Jump to a page. Unclamped here — see the note below.
next_page(page_count)Step forward, staying inside 0..page_count.
prev_page()Step back, never below 0.
set_page_size(n)Change rows-per-page, clamped to at least 1. Resets to page 0.
set_page accepts anything; the source clamps. The state does not know page_count — that comes out of a query, and holding a stale copy of it is worse than not holding one. So set_page stores what you gave it and ClientSource clamps into range when it runs, reporting the effective page back on the ResultSet. next_page is the exception: it takes page_count as an argument because "one more, unless that is past the end" cannot be expressed otherwise.

Selection intents

Selection is keyed by the grid's row_id string, not by index, so it survives sorting, filtering and paging. Selecting a row on page 1 and then jumping to page 4 keeps that row selected — which is what makes the bulk-action bar's count meaningful.

MethodEffect
is_selected(id)bool — is this row in the set.
selection_count()usize — total selected, across all pages.
selected_ids()Vec<String>, unordered — it comes from a HashSet. Sort at the call site if display order matters.
is_page_selected(page_ids)bool — every id on the page is selected and the page is non-empty.
toggle_row(id)Flip one row's membership.
toggle_page(page_ids)Select the whole page, or deselect it if already fully selected.
clear_selection()Empty the set.

#The transitions worth knowing

These are the behaviors that would otherwise be reimplemented — subtly differently — in every renderer. They live here precisely so they are pinned by tests.

Sort cycles through three states

Clicking the same header goes ascending → descending → unsorted, then back to ascending. Clicking a different column jumps straight to ascending rather than continuing the previous column's cycle.

tri-state sort
let mut s = GridState::new(10, false);

s.toggle_sort("name");   // Some(Sort::asc("name"))
s.toggle_sort("name");   // Some(Sort::desc("name"))
s.toggle_sort("name");   // None — unsorted

s.toggle_sort("name");   // asc again
s.toggle_sort("score");  // a NEW column starts at asc, not desc

Unsorted is a real third state, not a quirk. It is how a user gets back to the dataset's natural order — insertion order, or whatever the server sent — which is often meaningful and otherwise unreachable once they have sorted anything.

Query changes reset the page

set_search, clear_search, toggle_sort and set_page_size all snap back to page 0. If they did not, a user on page 7 who types a search that matches four rows would land on an empty page and conclude there were no results.

set_view is deliberately not in that list. Switching between table and gallery is a presentation change over the same rows, so losing your place would be a bug.

Page selection toggles as a unit

toggle_page looks at whether the page is already fully selected. If it is, it deselects those ids; otherwise it selects all of them. So a partially selected page tops up to full rather than clearing — the behavior a user expects from a header checkbox, and the reason the header control's label flips between "Select" and "Deselect".

An empty page is never considered fully selected, so is_page_selected(&[]) is false and the header checkbox on an empty grid does not read as checked.

page selection
let page = vec!["a".to_string(), "b".to_string()];

s.toggle_row("b");          // partial: 1 of 2
s.toggle_page(&page);      // not full → select all → 2 of 2
s.toggle_page(&page);      // full → deselect page → 0

Paging is clamped at both ends

prev_page at page 0 is a no-op, and next_page(count) on the last page is a no-op. Neither underflows, which matters because page is a usize.

#Driving it yourself

If you are building your own renderer, the whole integration is a state value, an intent call, and a re-query.

a renderer's frame
use grid_state::{GridState, ViewMode};

// held across frames
let mut state = GridState::new(25, false);

// on a header click
state.toggle_sort("name");

// draw
let page = source.query(state.model());
let ids: Vec<String> = page.rows.iter().map(row_id).collect();

let header_dir  = state.sort_dir_for("name");      // aria-sort / data-sorted
let all_checked = state.is_page_selected(&ids);   // header checkbox
let as_cards    = state.view().is_card();

Note that the ids handed to is_page_selected and toggle_page are the ids of the currently visible page, recomputed each frame from the query result. The state does not cache them, so the header checkbox is always about what is actually on screen.
