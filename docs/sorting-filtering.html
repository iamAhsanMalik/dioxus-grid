Sorting & filtering

Search narrows, filters narrow further, then sort orders what is left and pagination windows it. All four run over the same column projections, in that order, in pure code you can unit test without a browser.

#The pipeline

Every frame the grid assembles a GridQuery from its UI state and hands it to a provider, which answers with one GridPage:

Order of operations
global search  →  column filters  →  sort  →  paginate

The order matters for the numbers you see. Footer aggregates are computed after filtering and before pagination, so a total reflects every matching row rather than the visible page. Pagination is last, which is why changing a filter can move you onto a page that no longer exists — the page index is clamped into range rather than left dangling.

The query is memoized. It re-runs only when a query-defining signal changes — search, filters, sort, page, page size, or the dataset — never on scroll, hover or a menu toggle. That is what keeps a very large grid from re-filtering on every frame.

#Global search

Search is a single case-insensitive substring test against one string per row, which you supply:

The search haystack
DataGrid {
    rows,
    columns,
    row_id: |p: &Product| p.id.to_string(),
    search_text: Some((|p: &Product| format!("{} {} {}", p.name, p.sku, p.category))
        as fn(&Product) -> String),
}

One projection, not one per column, because that is what users mean by a search box: type anything, match anywhere. You decide what is searchable by deciding what goes into the string — including fields you never render, which is a cheap way to make internal identifiers findable.

Omitting search_text hides the search box entirely rather than rendering a box that does nothing.

#Column sort

Clicking a header cycles that column tri-state, and clicking a different column jumps straight to ascending:

Tri-state cycle
unsorted  →  ascending  →  descending  →  unsorted

The third click returning to unsorted is the part people forget to build. It matters because a dataset's natural order — insertion, relevance, whatever your Vec holds — is real information, and without an "off" state a user who sorts once can never get back to it.

Sorting always resets to page 0. Staying on page 7 of a freshly reordered list shows you rows that have nothing to do with what you clicked.

The state machine lives in grid-state and is directly testable:

Driving GridState by hand
use grid_state::GridState;

let mut s = GridState::new(10, false);
s.set_page(3);
s.toggle_sort("name");              // ascending, and page → 0
assert_eq!(s.sort_dir_for("name"), Some(true));
s.toggle_sort("name");              // descending
assert_eq!(s.sort_dir_for("name"), Some(false));
s.toggle_sort("name");              // off
assert_eq!(s.sort(), None);

sort_dir_for(key) returns Some(true) for ascending, Some(false) for descending and None when that column is not the sorted one — which is exactly what a header needs to pick its indicator.

#Multi-column sort

Shift-clicking a header adds it as a tie-breaker after the primary sort, cycling ascending → descending → removed, leaving the primary untouched. A plain click sets the primary and clears the tie-breakers, so there is always an obvious way back to a simple sort.

Underneath, this builds a MultiSort whose comparators are applied left to right, the first being primary. Grouping prepends the group column so same-value rows stay contiguous; your sort then orders rows within each group.

Composing sorts directly
use grid_plugin_api::{MultiSort, Sort};

let sort = MultiSort::new()
    .then(Sort::asc("department"))
    .then(Sort::desc("salary"));

Sorting is stable, so equal rows keep their previous relative order. A column with no projection is skipped in the comparison rather than treated as equal.

#Per-column filters

Each filterable header carries a funnel that opens a popover — a bottom sheet on mobile. A column is filterable when it has a projection, meaning any column you made sortable is filterable already. Active filters appear as chips above the table so a narrowed grid never looks like an empty one.

Filters combine with AND by default: a row must satisfy every active column filter.

Filtering a hidden column still works. The column chooser hides, it never removes. A hidden column's filter and sort keep applying, and it still appears in exports — otherwise "tidy up the view" would silently change your results.

#FilterKind

The control shown in the popover is inferred from the column, and you can set it explicitly with .filter(FilterKind::…). All kinds drive the same underlying filter stage over the same projection; only the input differs.

VariantControlUse for
AutoInferred: Number if the column has a numeric projection, else Text.The default; usually right.
TextOperator picker plus a text input.Names, descriptions, free text.
NumberOperator picker plus a number input.Quantities, prices, counts.
SetCheckbox list of the column's distinct values.Enums: status, department, category.
RangeTwo optional numeric bounds, min and max.Duration, file size, price bands.
DateRangeTwo date pickers, from and to.ISO YYYY-MM-DD date columns.
RatingA 0–5 star picker meaning "at least N".Review scores.
HasValueA present / absent toggle.Attachments, optional media, nullable fields.
Choosing filter controls
use grid_dioxus::{FilterKind, GridColumn};

let columns = vec![
    // Distinct values become checkboxes — the natural control for an enum.
    GridColumn::new("category", "Category", |p: &Product| rsx! { "{p.category}" })
        .sortable(|p: &Product| p.category.clone())
        .filter(FilterKind::Set),

    // A min–max band reads better than ">" then "<" as two separate filters.
    GridColumn::new("price", "Price", |p: &Product| rsx! { "${p.price:.2}" })
        .sortable_num(|p: &Product| p.price)
        .filter(FilterKind::Range),

    // An empty projection means "absent", so a plain String works.
    GridColumn::new("spec", "Datasheet", |p: &Product| rsx! { "{p.spec_file}" })
        .sortable(|p: &Product| p.spec_file.clone())
        .filter(FilterKind::HasValue),
];

Set derives its choices from the dataset, sorted and de-duplicated, and caps the list so a high-cardinality column cannot render thousands of checkboxes. It needs a text projection — .sortable(…) — because it lists values as strings.

A Set filter needs .sortable(), not .sortable_num(). The checklist is built from the string sort key, so a column that only declares a numeric key has nothing to enumerate and the popover renders “No values” with no error. If you wanted a custom order — say status by workflow stage rather than alphabetically — you have to choose: numeric sorting, or a Set filter. One column cannot have both.

DateRange compares lexicographically over the text projection, which is chronological precisely because ISO YYYY-MM-DD sorts that way. Project your dates in that format and range filtering is free; a localised string like "25/07/2026" will not order correctly.

Date pickers need to know what "today" is, and the grid keeps itself clock-free so it stays deterministic. Pass today as an ISO string if you want the presets and the today marker to be correct:

Supplying the clock
DataGrid {
    rows,
    columns,
    row_id: |o: &Order| o.id.to_string(),
    today: Some("2026-07-25".to_string()),
}

#Operators

The text and number controls offer a subset of FilterOp chosen to suit the column: comparison operators for numeric columns, substring operators for text, equality and emptiness for both. The full set, from grid-plugin-api:

OperatorMeaning
EqualsCell equals the operand.
NotEqualsCell differs from the operand.
ContainsCase-insensitive substring. Non-text cells never match.
StartsWithCase-insensitive prefix.
GreaterThanOrdered comparison.
GreaterOrEqualOrdered comparison.
LessThanOrdered comparison.
LessOrEqualOrdered comparison.
IsEmptyCell is empty. Blank or whitespace-only text counts as empty. Ignores the operand.
IsNotEmptyCell has content. Ignores the operand.
InCell equals any member of a value set. An empty set matches nothing.

IsEmpty treating whitespace-only text as empty is what lets a column expose presence with a plain String projection — "" for absent — rather than needing a typed cell value. It is the mechanism behind FilterKind::HasValue.

The richer kinds compile down to these same operators: Range becomes up to two comparisons, Rating a single GreaterOrEqual, Set one In. There is one filter engine, not eight.

#Building filters in code

The headless crates are usable on their own — for tests, for a server-side implementation of the same query, or for a non-Dioxus front end.

A filter model by hand
use grid_plugin_api::{CellValue, Filter, FilterModel, FilterOp};

// ANDed by default.
let model = FilterModel::new()
    .with(Filter::contains("name", "widget"))
    .with(Filter::greater_than("price", CellValue::Number(100.0)));

// A set filter, and an OR combination.
let either = FilterModel::new()
    .with(Filter::one_of("department", vec!["eng".into(), "ops".into()]))
    .with(Filter::new("note", FilterOp::IsNotEmpty, CellValue::Empty))
    .any();

A filter naming a column that does not exist, or one with no projection, is inert — it is skipped, not treated as matching nothing. Dropping every row because of a typo in a key is the worse failure mode.

#Server-side querying

Past what a browser can hold, move the pipeline to the server. Supply on_query and the grid stops querying rows: it emits the effective GridQuery on every change and renders whatever page you feed back through remote_page.

Remote mode
use grid_dioxus::{GridPage, GridQuery};

let mut page = use_signal(|| None::<GridPage<Product>>);

rsx! {
    DataGrid {
        rows: std::rc::Rc::from(vec![]),   // unused in remote mode
        columns,
        row_id: |p: &Product| p.id.to_string(),
        on_query: move |q: GridQuery| {
            spawn(async move {
                page.set(fetch_products(q).await.ok());
            });
        },
        remote_page: page(),
        loading: page().is_none(),
    }
}

GridQuery and GridPage are the same types the local provider uses, so switching a grid from in-memory to server-side is a provider swap and not a renderer change. With the serde feature on grid-plugin-api, GridQuery serialises directly — your endpoint can accept it verbatim.

Validate the query on the server. A GridQuery arriving over the wire is user input. Check the column keys against a whitelist and cap page_size before it reaches your database, exactly as you would with any other query parameters.
