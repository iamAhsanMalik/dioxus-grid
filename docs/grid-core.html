Crates

grid-core

The data-operations engine. It owns the vocabulary a grid uses to describe what it wants — a query, a sort, a column's sortable projection — and the pipeline that turns that into a page of rows. No UI, no framework, no DOM. #![forbid(unsafe_code)], 20 unit tests and a doctest.

You rarely add this to your manifest. grid-dioxus re-exports it as grid_dioxus::grid_core. Depend on it directly only when you are building a non-Dioxus renderer or testing query logic in isolation.

#CellValue

The typed basis for comparison. A fn(&T) -> String sort key has to allocate a lowercased String on every comparison, which is fine at a few hundred rows and quadratically wasteful past that. A column can instead project each row to a CellValue once, after which comparisons are allocation-free.

grid_core::CellValue
pub enum CellValue {
    Empty,
    Bool(bool),
    Int(i64),
    Number(f64),
    Text(String),
}

From is implemented for &str, String, i64, f64 and bool, so "eng".into() and 42i64.into() both work at a call site.

Total ordering

CellValue implements Ord, so it can drive sort_by directly. The order is defined so that no input can panic and no input leaves two values incomparable:

  • Empty sorts first. Blanks lead in ascending order.
  • Text compares case-insensitively, matching the older string-key path so switching a column to .typed does not reorder it.
  • Int and Number compare numerically across variants — Int(10) < Number(10.5), and Number(2.0) == Int(2).
  • NaN sorts last and never panics. A NaN is greater than every non-NaN, and two NaNs compare equal.
  • Genuinely mixed variants fall back to a fixed rank, Bool < Int < Number < Text. Mixing types in one column is a caller mistake, but it must produce a stable, total order rather than an inconsistent comparator.
Number(NaN) == Number(NaN) is true here. This deliberately differs from raw f64. Eq and Ord have to be reflexive, so equality is defined via the total order rather than delegating to float semantics. The practical payoff is that a column full of NaNs sorts and dedups sanely instead of triggering the "comparison function does not implement a total order" panic from sort_by.

#Sort

A single-column sort instruction. ascending: true is the column's natural order; false reverses it.

grid_core::Sort
pub struct Sort {
    pub key: Cow<'static, str>,
    pub ascending: bool,
}

impl Sort {
    pub fn new(key: impl Into<Cow<'static, str>>, ascending: bool) -> Self;
    pub fn asc(key: impl Into<Cow<'static, str>>) -> Self;
    pub fn desc(key: impl Into<Cow<'static, str>>) -> Self;
    pub fn key(&self) -> &str;
}

The key is a Cow<'static, str> rather than a String for a specific reason. In process, a column key is a &'static str, so building a Sort costs nothing. But the same type has to survive a round trip through a server: deserializing a query yields an owned key, and Cow covers both without two types or a lifetime parameter on the query. Read it as &str with Sort::key().

#ColumnDef

The data-relevant half of a column: how to sort it. Note what is not here — no render, no label, no alignment, no width. Those are view concerns and live in the renderer's own column type (GridColumn). Keeping them apart is what lets the engine be tested without a DOM.

grid_core::ColumnDef
pub struct ColumnDef<T> {
    pub key: &'static str,
    pub value: Option<fn(&T) -> CellValue>,
    pub sort_key: Option<fn(&T) -> String>,
    pub sort_num: Option<fn(&T) -> f64>,
}

impl<T> ColumnDef<T> {
    pub fn new(key: &'static str) -> Self;
    pub fn typed(self, f: fn(&T) -> CellValue) -> Self;
    pub fn sortable(self, f: fn(&T) -> String) -> Self;
    pub fn sortable_num(self, f: fn(&T) -> f64) -> Self;
}

Sort key precedence is value, then sort_num, then sort_key. A column may declare more than one; the typed projection always wins. This is what makes .typed adoptable incrementally — add it to a hot column and the older keys become inert without you having to delete them.

A column with no projection at all is simply not sortable. The pipeline skips an unknown or unprojectable sort key rather than erroring or reordering arbitrarily.

#QueryModel

The complete description of a view: what to search, how to sort, which page. It is plain cloneable data, which is the whole point — the same model can be evaluated in memory today and posted to a server tomorrow without changing the call site.

grid_core::QueryModel
pub struct QueryModel {
    pub search: String,      // empty after trim = no filter
    pub sort: Option<Sort>,
    pub page: usize,        // zero-based; clamped by the source
    pub page_size: usize,   // clamped to at least 1
}

impl QueryModel {
    pub fn new(page_size: usize) -> Self;
    pub fn with_search(self, q: impl Into<String>) -> Self;
    pub fn with_sort(self, sort: Sort) -> Self;
    pub fn with_page(self, page: usize) -> Self;
}

#ResultSet

The materialised window a renderer draws. total is the count after filtering but before pagination, which is what a footer needs; page is the index after clamping, so a renderer can trust it even if the caller asked for page 900 of 3.

grid_core::ResultSet
pub struct ResultSet<T> {
    pub rows: Vec<T>,
    pub total: usize,
    pub page: usize,
    pub page_count: usize,   // always at least 1
}

impl<T> ResultSet<T> {
    // 1-based bounds for "Showing X–Y of N". `from_index` is 0 when empty.
    pub fn from_index(&self, page_size: usize) -> usize;
    pub fn to_index(&self, page_size: usize) -> usize;
}

from_index and to_index exist so that every renderer computes the "Showing 21–40 of 137" label the same way, including the two edge cases that are easy to get wrong: an empty result set reports 0 rather than 1, and a partial last page reports the real row count rather than page * page_size.

#DataSource

One method, and the seam that makes client-side and server-side grids the same code path.

grid_core::DataSource
pub trait DataSource<T> {
    fn query(&self, model: &QueryModel) -> ResultSet<T>;
}

The trait is object-safe, so a renderer can hold a Box<dyn DataSource<T>> and swap a local dataset for a remote one at runtime.

ClientSource

The in-memory implementation, running the pipeline over a Vec<T>.

grid_core::ClientSource
pub struct ClientSource<T> {
    pub rows: Vec<T>,
    pub columns: Vec<ColumnDef<T>>,
    pub search_text: Option<fn(&T) -> String>,
}

impl<T: Clone> ClientSource<T> {
    pub fn new(rows: Vec<T>, columns: Vec<ColumnDef<T>>) -> Self;
    pub fn searchable(self, f: fn(&T) -> String) -> Self;
}

searchable attaches the projection the global search box matches against — typically a format! of the fields a user would type. Leave it off and the search term is ignored rather than matching nothing, which is the behavior you want for a grid with no search box.

a query, end to end
use grid_core::{ClientSource, ColumnDef, DataSource, QueryModel, Sort};

let src = ClientSource::new(members, vec![
        ColumnDef::new("name").sortable(|m: &Member| m.name.clone()),
        ColumnDef::new("score").sortable_num(|m: &Member| m.score),
    ])
    .searchable(|m: &Member| format!("{} {}", m.name, m.email));

let page = src.query(
    &QueryModel::new(25).with_search("acme").with_sort(Sort::asc("name")),
);

println!("Showing {}–{} of {}",
    page.from_index(25), page.to_index(25), page.total);

RemoteSource

The server-side counterpart: the backend does the filtering, sorting and pagination, and this hands back the page it returned.

grid_core::RemoteSource
pub struct RemoteSource<T, F: Fn(&QueryModel) -> ResultSet<T>> { /* … */ }

impl<T, F: Fn(&QueryModel) -> ResultSet<T>> RemoteSource<T, F> {
    pub fn new(fetch: F) -> Self;
}

The fetcher is synchronous, which surprises people, so it is worth stating why. A headless engine must not pick your async runtime or your HTTP client. So the host awaits the real request outside this call — in Dioxus, typically a use_resource — and once it resolves, wraps the already-fetched ResultSet in a RemoteSource. The engine stays sync, pure and runtime-free, and DataSource remains one trait shared with ClientSource.

#Pipeline order

ClientSource::query runs three stages, in this order, and the order is load-bearing.

StageBehavior
1. Filter Case-insensitive substring match of the trimmed search term against the search_text projection. An empty or whitespace-only term is a no-op; no projection means the term is ignored.
2. Sort Resolves the sort key's column, then uses value / sort_num / sort_key in that precedence. Descending reverses the sorted list, so all three key paths stay consistent. An unknown key is a no-op.
3. Paginate page_size is clamped to at least 1, page_count to at least 1, and page into 0..page_count. An out-of-range page lands on the last page rather than returning nothing.

Filtering before sorting means the sort only touches surviving rows. Sorting before pagination means the page is a window into the ordered set rather than an ordering of an arbitrary window — the difference between a correct grid and a confusing one.

#The serde feature

Optional and off by default. Enabling it derives Serialize and Deserialize for CellValue, Sort and QueryModel — the types that cross a wire when a grid goes server-side. It is off by default because a purely client-side grid should not pull in serde to satisfy a feature it never uses.

Cargo.toml
[dependencies]
grid-core = { version = "0.1", features = ["serde"] }

A QueryModel whose sort key came from a &'static str serializes to JSON and parses back to an owned, equal model — that round trip is exactly what the Cow key is for, and it is covered by a test.
