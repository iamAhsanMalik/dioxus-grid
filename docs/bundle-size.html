Guides

Bundle size

DataGrid<T> is generic, so a naive build code-generates the entire render body once per row type. On native that is free speed. In wasm it is a dozen copies of a 2,500-line component shipped over the wire. The crate therefore compiles one of two render bodies, and picks for you based on the target.

#The monomorphization problem

Rust generics are monomorphized: DataGrid<User> and DataGrid<Invoice> are two separate functions in the final binary, each a full copy of the render logic. That is exactly what you want for a small generic helper, and exactly what you do not want for the largest component in the crate.

The renderer is big because a real grid is big — the header with its sort controls and per-column filter popovers, the body with inline editing and keyboard navigation, group headers, the totals row, the card view, the toolbar, the export menu, the bulk-action bar, the pagination footer. An application with ten entity types and one grid per screen pays for that surface ten times.

Native builds do not care. The binary lives on disk, nobody downloads it, and monomorphization is what lets the optimizer specialize each row type's code. A wasm build cares enormously, because every byte is on the critical path of a first page load.

#Two render paths

So there are two implementations of the render body, and exactly one of them is compiled into any given build.

Type-erased

A thin generic shell does all the T-specific work up front — running the engine query, projecting each visible row's cells to plain Elements, boxing the per-row callbacks — and hands the result to a single non-generic renderer. Only the shell is generated per row type; the body compiles once no matter how many row types the app has. Default on wasm32.

Monomorphized

The render body is generic over T and inlines the row projections directly, so there is no snapshot allocation and no boxed callback indirection per row. A copy per row type, which costs nothing where binary size is irrelevant. Default on native targets.

The seam is a snapshot type. In erased mode the shell builds an ErasedGrid that carries no T anywhere: columns reduce to display metadata, each visible row becomes an id plus a Vec<Element> of already-rendered cells, and callbacks that need to hand a row back to the host are captured as closures over the original Rc<[T]>. Row identity and round-trips stay correct because the closures still close over the real data — the renderer simply never sees its type.

Note what stays generic either way: the query pipeline from grid-core, grid-state and grid-plugin-api still runs in the per-type shell. That is fine. The engine is small; the size lives in the renderer, and that is what erasure targets.

#Why the choice is compile-time

This cannot be a runtime flag, and the distinction matters if you are tempted to ask for one. Erased-versus-monomorphized is a codegen decision: the whole benefit is that the compiler never emits the per-type copies at all. A runtime branch would require both bodies to exist in the binary, which is strictly larger than either — the exact opposite of the goal.

The resolution therefore lives in build.rs, which sets one of two cfgs, and the rest of the crate keys off those so the policy exists in exactly one place.

grid-dioxus/build.rs — the policy
let erased = if force_mono {
    false
} else if force_erased {
    true
} else {
    is_wasm  // CARGO_CFG_TARGET_ARCH == "wasm32"
};

if erased {
    println!("cargo::rustc-cfg=grid_erased");
} else {
    println!("cargo::rustc-cfg=grid_mono");
}

Downstream code — including the crate's own modules — then reads only the cfg aliases, never the features:

grid-dioxus/src/mode.rs
#[cfg(grid_erased)]  fn render() { /* erased path */ }
#[cfg(grid_mono)]    fn render() { /* monomorphized path */ }

The two cfgs are declared with cargo::rustc-check-cfg, so building under -D warnings stays quiet, and consuming crates never need to declare them.

#Overriding the default

The target-based default is right for nearly every build. Two features exist for when it is not.

ConfigurationRender pathWhen
neither feature (default) erased on wasm32, monomorphized elsewhere Almost always. Leave it alone.
force-mono always monomorphized A wasm build with exactly one row type, where you would rather have the specialized code than the shared body — or you are profiling the difference.
force-erased always erased A native build where binary size genuinely matters (an embedded target, a size-budgeted CLI), or you want desktop and web to exercise the same code path in tests.
Cargo.toml
[dependencies]
# default: erased in wasm, monomorphized on native
grid-dioxus = { version = "0.1", features = ["web"] }

# or pin the path explicitly
grid-dioxus = { version = "0.1", features = ["web", "force-erased"] }
Enabling both is a compile error. force-mono and force-erased are contradictory, so mode.rs fails the build with a compile_error! naming both features rather than letting one silently win. This matters because Cargo unifies features across a workspace — if two crates in your tree each pick a different override, you want to hear about it at compile time, not wonder why your wasm grew.
The erased path does not render the export control. The snapshot carries export_filename through, but the non-generic renderer has no export button yet, so the CSV, Excel and PDF menu appears on the monomorphized path only. Since wasm defaults to erased, a browser build shows no export UI unless you opt into force-mono. Sorting, filtering, selection, grouping, inline edit, the card view and paging are identical on both paths.

#What it measures

For the example app in examples/basic, a release wasm build comes out at roughly 2.0 MB raw and 579 KB gzipped — the number that actually crosses the network. That figure includes the Dioxus runtime and the demo itself, not just the grid.

Treat it as an order of magnitude rather than a target to hit. Your own number depends on how many row types you instantiate, which features you enable, and what else is in your binary. The useful property is not the absolute size but the slope: on the erased path, adding an eleventh grid over an eleventh row type adds a shell, not another renderer.

#Features that affect size

Everything is off by default, so you opt into weight rather than stripping it out.

FeaturePulls inEffect
web dioxus/web, web-sys (Window, Storage) Browser glue. Persists column layout — order, widths, pins, hidden columns — to localStorage under the grid's persist_key. Cheap; on native every call is a no-op.
export-rich rust_xlsxwriter, krilla Client-side Excel and PDF encoders. These are heavyweight binary-format crates. CSV export always works without this feature and has no dependencies.
force-mono / force-erased — Override the render path above. At most one.
Leave export-rich off for wasm. Producing a signed or styled document in the browser means shipping two binary-format encoders to every visitor. In practice these belong on the server — which is why the grid also exposes on_export_signed, handing your backend the current GridQuery so it can render, sign and return the file. The grid never signs anything: signing keys cannot live in a browser.
