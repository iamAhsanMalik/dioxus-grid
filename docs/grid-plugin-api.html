grid-plugin-api

Composable query stages, and the data-provider seam. Column filtering, multi-column sort and aggregation are all the same shape — a transform on the row pipeline — so they are all one trait. Adding a capability means adding a stage, not editing the engine. #![forbid(unsafe_code)], 18 tests.

This crate composes with grid-core rather than changing it: it carries its own extended model, and its Pipeline yields the same ResultSet the plain engine does, so a plugin-powered grid drives an unmodified renderer. It re-exports CellValue and Sort, so you can build filters and sorts depending on this crate alone.

#QueryStage — the extension seam

One method. Given the rows so far and the columns (for their value projections), return the rows that survive — filtered, reordered, whatever the stage does.

grid_plugin_api::QueryStage
pub trait QueryStage<T> {
    fn apply(&self, rows: Vec<T>, columns: &[ColumnDef<T>]) -> Vec<T>;
}

That is the whole plugin contract. A new capability — range filters, a custom grouping, a domain-specific ranking — is a new QueryStage implementation, and nothing else in the engine changes. The stage receives the columns rather than reaching for them so it can resolve projections by key without knowing anything about T.

Projection resolution

A stage turns a column key into a Projection<T>, which is just a boxed row-to-value function:

grid_plugin_api
pub type Projection<T> = Box<dyn Fn(&T) -> CellValue>;

// An owned/borrowed column key, mirroring grid_core::Sort's key type.
pub type Cow = std::borrow::Cow<'static, str>;

Resolution uses the same precedence as core's sort: typed value, then sort_num (wrapped as CellValue::Number), then sort_key (wrapped as CellValue::Text).

Sortable implies filterable. Because filtering reuses the sort projection, any column you already made sortable is filterable, groupable and aggregatable with no extra configuration. A column declared the old way with .sortable(…) and no .typed(…) still filters correctly through the Text fallback — which is what let this crate be added to existing grids with zero call-site changes.

A column with no projection, or a key that matches no column, resolves to None, and the stages then skip that filter or sort. They never drop rows because a key was wrong — an inert filter is a recoverable mistake, a silently empty grid is not.

#Column filters

grid_plugin_api::FilterOp
pub enum FilterOp {
    Equals, NotEquals,
    Contains,        // text, case-insensitive; non-text never matches
    StartsWith,      // text, case-insensitive
    GreaterThan, GreaterOrEqual, LessThan, LessOrEqual,
    IsEmpty, IsNotEmpty,   // `value` ignored
    In,              // matches any of `values`; empty set matches nothing
}

The comparison operators run on CellValue's total order, so they work uniformly on numbers, text and booleans without per-type branching, and a NaN cannot make them panic.

grid_plugin_api::Filter
pub struct Filter {
    pub key: Cow,
    pub op: FilterOp,
    pub value: CellValue,
    pub values: Vec<CellValue>,   // only for FilterOp::In
}

impl Filter {
    pub fn new(key: impl Into<Cow>, op: FilterOp, value: impl Into<CellValue>) -> Self;
    pub fn one_of(key: impl Into<Cow>, values: Vec<CellValue>) -> Self;
    pub fn equals(key: impl Into<Cow>, value: impl Into<CellValue>) -> Self;
    pub fn contains(key: impl Into<Cow>, value: impl Into<CellValue>) -> Self;
    pub fn greater_than(key: impl Into<Cow>, value: impl Into<CellValue>) -> Self;
    pub fn less_than(key: impl Into<Cow>, value: impl Into<CellValue>) -> Self;
    pub fn is_empty(key: impl Into<Cow>) -> Self;

    // Evaluate against one already-projected cell — public so an
    // index-based provider can test a row without cloning it.
    pub fn matches_value(&self, cell: &CellValue) -> bool;
}
IsEmpty treats blank text as empty. A cell counts as empty if it is CellValue::Empty or it is Text that trims to nothing. This lets a column expose presence with a plain string projection — "" for absent — instead of requiring a typed CellValue, which is what powers the "has file / no file" style filters.

FilterModel and Combine

grid_plugin_api
pub enum Combine { All, Any }   // All is the default

pub struct FilterModel {
    pub filters: Vec<Filter>,
    pub combine: Combine,
}

impl FilterModel {
    pub fn new() -> Self;
    pub fn with(self, f: Filter) -> Self;   // ANDed by default
    pub fn any(self) -> Self;             // switch to OR
    pub fn is_empty(&self) -> bool;
}

pub struct FilterStage<'a> { pub model: &'a FilterModel }
impl<'a> FilterStage<'a> {
    pub fn new(model: &'a FilterModel) -> Self;
}

An empty FilterModel is pass-through. The stage resolves each filter's projection once before scanning, not once per row, so a five-filter query over 50,000 rows does five boxed lookups rather than 250,000.

#Multi-column sort

Sort by several columns, tie-broken left to right: the first Sort is primary. Columns with no projection are skipped in the comparison rather than treated as equal-everything.

grid_plugin_api
pub struct MultiSort { pub sorts: Vec<Sort> }

impl MultiSort {
    pub fn new() -> Self;
    pub fn then(self, sort: Sort) -> Self;
    pub fn is_empty(&self) -> bool;
}

pub struct MultiSortStage<'a> { pub model: &'a MultiSort }
impl<'a> MultiSortStage<'a> {
    pub fn new(model: &'a MultiSort) -> Self;
}
department ascending, then age descending within each
let ms = MultiSort::new()
    .then(Sort::asc("dept"))
    .then(Sort::desc("age"));

let rows = MultiSortStage::new(&ms).apply(rows, &columns);

The sort is stable, so rows equal on every key keep their incoming relative order.

#Aggregates

grid_plugin_api
pub enum Aggregate { Sum, Avg, Min, Max, Count }

pub enum AggValue {
    Num(f64),      // Sum / Avg / Min / Max
    Count(usize),   // Count
    Empty,          // nothing numeric to aggregate
}

pub fn aggregate<T: 'static>(
    rows: &[T],
    columns: &[ColumnDef<T>],
    key: &str,
    agg: Aggregate,
) -> AggValue;

Numeric aggregates pull values through the same projection fallback and accept only Int and non-NaN Number cells; text and NaN are skipped. Sum over an all-text column is therefore AggValue::Empty, not Num(0.0) — the distinction between "the total is zero" and "there is no total" is one a footer should render differently. Count is type-agnostic and counts rows.

In a grid you aggregate over the filtered set, not the page — a footer total that changes when you turn the page is a bug. That is what Pipeline::filtered below is for.

#Pipeline

Composes global search, an ordered list of stages, and pagination into a single ResultSet.

grid_plugin_api::Pipeline
impl<'c, T: Clone + 'static> Pipeline<'c, T> {
    pub fn new(rows: Vec<T>, columns: &'c [ColumnDef<T>]) -> Self;
    pub fn search(self, f: fn(&T) -> String) -> Self;
    pub fn search_opt(self, f: Option<fn(&T) -> String>) -> Self;
    pub fn stage(self, stage: impl QueryStage<T> + 'c) -> Self;

    // search → stages, ALL matching rows (before pagination)
    pub fn filtered(self, model: &QueryModel) -> Vec<T>;
    // search → stages → paginate
    pub fn run(self, model: &QueryModel) -> ResultSet<T>;
}

// The same pagination arithmetic, exposed on its own.
pub fn paginate<T>(rows: Vec<T>, model: &QueryModel) -> ResultSet<T>;

Global search always runs first, matching ClientSource's behavior exactly — trimmed, lowercased substring, and a no-op when there is no projection. Then stages run in the order you added them. Then pagination.

filtered and run exist as a pair because a grid needs both from one query: run for the page to draw, and filtered for the footer aggregates and for "export everything I can currently see", which must span all pages.

composing a query
use grid_core::{CellValue, ColumnDef, QueryModel};
use grid_plugin_api::{Filter, FilterModel, FilterStage, Pipeline};

let cols = vec![
    ColumnDef::new("name").typed(|r: &Row| r.name.into()),
    ColumnDef::new("age").typed(|r: &Row| CellValue::Int(r.age)),
];

let filter = FilterModel::new()
    .with(Filter::greater_than("age", CellValue::Int(20)));

let out = Pipeline::new(rows, &cols)
    .search(|r: &Row| r.name.to_string())
    .stage(FilterStage::new(&filter))
    .run(&QueryModel::new(10));

#DataProvider

The seam the renderer actually talks to. A renderer builds a GridQuery from its UI state and gets back one GridPage. It never learns whether the answer came from memory or from a server.

grid_plugin_api
pub struct GridQuery {
    pub search: String,
    pub filters: FilterModel,
    pub sort: MultiSort,
    pub page: usize,
    pub page_size: usize,
    // (column key, aggregate) pairs to compute over the filtered set
    pub aggregates: Vec<(String, Aggregate)>,
}
impl GridQuery {
    pub fn new(page_size: usize) -> Self;
}

pub struct GridPage<T> {
    pub rows: Vec<T>,
    pub total: usize,
    pub page: usize,
    pub page_count: usize,
    pub aggregates: Vec<(String, AggValue)>,
}

pub trait DataProvider<T> {
    fn query(&self, q: &GridQuery) -> GridPage<T>;
}

GridQuery is the complete, transport-agnostic request — search text, filters, sort order, page window, and which columns want a footer aggregate. Because the query and page types are identical for both provider kinds, moving a grid from local to server-side is a provider swap with no renderer change.

LocalProvider

grid_plugin_api::LocalProvider
impl<'c, T: Clone + 'static> LocalProvider<'c, T> {
    pub fn new(rows: Rc<[T]>, columns: &'c [ColumnDef<T>]) -> Self;
    pub fn search(self, f: fn(&T) -> String) -> Self;
    pub fn search_opt(self, f: Option<fn(&T) -> String>) -> Self;
}

It is index-based. The dataset is held as an Rc<[T]>, so handing the same rows to several grids, or re-rendering, is a refcount bump rather than a copy. A query then narrows a Vec<usize> of indices through search, filters and sort, aggregates over those indices, and only clones the rows in the final page window.

Concretely, a query over a large local dataset costs one shared pointer, an O(n) comparison scan, and page_size clones — never a clone of the whole dataset. This is the reason the grid's row prop is Rc<[T]> and not Vec<T>; the shape of the provider is where that requirement comes from.

Two supporting details make it work: Filter::matches_value is public, so the provider can test a projected value against a row reference without cloning it, and sort projections are resolved once per sort column rather than once per comparison.

A remote provider

You write it. Implement the same trait with the same query and page types, send the GridQuery to your backend, and return the page it computed. The browser then holds only what is on screen, which is how a grid scales past what a browser can hold at all.

The trait is synchronous, and a remote source is not. LocalProvider answers immediately, so DataProvider is sync. Real remote fetching is driven by the renderer through an async fetcher instead — in grid-dioxus that is the on_query / remote_page prop pair. Either way the result is a GridPage, so the drawing code is identical.

#The serde feature

Optional and off by default, matching grid-core. It derives Serialize and Deserialize for FilterOp, Filter, Combine, FilterModel, MultiSort, Aggregate and GridQuery — everything a server-side provider needs to put on the wire. Filter::values is skipped when empty, so the common single-operand filter serializes compactly.
