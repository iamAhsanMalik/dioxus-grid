Selection & paging

Selection is a set of row ids, so it survives sorting, filtering and paging. Pagination is clamped and resets on anything that changes the result set. Both state machines live in grid-state, which is why they behave the same way every time.

#Enabling selection

selectable: true adds a checkbox to each row and a select-page checkbox in the header. on_selection fires with the full set of selected ids whenever it changes.

Selection
let mut selected = use_signal(Vec::<String>::new);

rsx! {
    DataGrid {
        rows,
        columns,
        row_id: |p: &Product| p.id.to_string(),
        selectable: true,
        on_selection: move |ids: Vec<String>| selected.set(ids),
    }
}

The ids are whatever row_id produces, which is why that prop is required. Selection is keyed by identity rather than by row index or by row value: an index would break the moment the user sorted, and a value would break the moment anything was edited.

Selection is unordered. selected_ids() returns the set's contents in arbitrary order. If display order matters, sort the ids at the call site.

#Select page

The header checkbox is a page toggle, not a select-all. Pressing it selects every row on the current page — unless the page is already fully selected, in which case it deselects that page and leaves the rest of your selection alone.

It deliberately does not reach beyond the page. "Select all 40,000 matching rows" is a different, much more consequential action than "select these twenty", and conflating them is how people delete things they did not mean to. A partially selected page tops up to fully selected rather than clearing, which is the behaviour that matches what the click looks like.

Because selection is a set of ids, it accumulates across pages: check five rows, page forward, check five more, and you have ten selected. Nothing is dropped by navigating.

#Driving selection directly

The renderer holds a single GridState and calls intent methods on it. You can drive the same value yourself — in tests, or in a renderer of your own.

grid-state selection
use grid_state::GridState;

let mut s = GridState::new(10, false);
let page = vec!["a".to_string(), "b".to_string(), "c".to_string()];

s.toggle_row("b");
assert!(s.is_selected("b"));
assert_eq!(s.selection_count(), 1);

s.toggle_page(&page);            // partial → select the whole page
assert!(s.is_page_selected(&page));
assert_eq!(s.selection_count(), 3);

s.toggle_page(&page);            // full → deselect the whole page
assert_eq!(s.selection_count(), 0);

s.clear_selection();
MethodReturnsNotes
is_selected(&str)boolMembership by id.
selection_count()usizeTotal selected, across all pages.
selected_ids()Vec<String>Unordered.
is_page_selected(&[String])boolFalse for an empty page — nothing is not "all".
toggle_row(&str)—Add or remove one id.
toggle_page(&[String])—Select the page, or deselect it if already full.
clear_selection()—Empty the set.

#Bulk actions

Selection is only useful if you can act on it. Supplying on_bulk_action makes the grid build a bulk bar for you from the actions the selected rows already declare — the same GridActions their kebab menus offer.

Derived bulk bar
use grid_dioxus::GridAction;

DataGrid {
    rows,
    columns,
    row_id: |p: &Product| p.id.to_string(),
    selectable: true,
    actions: Some((|_p: &Product| vec![
        GridAction::new("edit", "Edit").no_bulk(),   // single-row only
        GridAction::new("archive", "Archive"),
        GridAction::danger("delete", "Delete"),
    ]) as fn(&Product) -> Vec<GridAction>),
    on_bulk_action: move |(key, rows): (&'static str, Vec<Product>)| {
        match key {
            "archive" => archive_all(&rows),
            "delete" => delete_all(&rows),
            _ => {}
        }
    },
}

The bar shows the intersection of the selected rows' actions, in the order the first row lists them. An action survives only if every selected row offers it and none of them mark it disabled. That falls out of the same per-row logic, so a bulk bar can never offer an operation that is invalid for one of the rows it would apply to.

Handlers receive the resolved Vec<T>, not ids, so you do not look rows back up yourself.

GridActionEffect
GridAction::new(key, label)A normal entry.
GridAction::danger(key, label)Marked destructive, for your CSS to style.
.icon(path)A leading icon: SVG path data on a 24×24 stroke-based viewBox.
.quick()Also surface it inline beside the kebab. Requires an icon.
.disabled()Shown but not actionable; excluded from bulk.
.no_bulk()Single-row only — kept in the kebab, omitted from the bulk bar.

.no_bulk() exists for actions that are meaningless in aggregate. "Edit" opens one record's form; offering it for forty selected rows is a bug waiting to be reported.

For UI the derived bar cannot express, the bulk prop takes an Element rendered in the toolbar whenever at least one row is selected. It renders in addition to the derived bar, so you can have both.

#Pagination

The footer shows the current range, a rows-per-page picker (10, 25, 50, 100) and previous/next buttons, which disable at the ends rather than wrapping.

Page size
DataGrid {
    rows,
    columns,
    row_id: |p: &Product| p.id.to_string(),
    page_size: 25,        // initial value; defaults to 10, clamped to ≥ 1
}

Two rules keep the page index honest:

  • Anything that changes the result set resets to page 0. Search, sort and page size all do. Page 7 of a re-sorted list is a different seven pages of data, so keeping the index would show rows unrelated to what the user just did.
  • Paging is clamped into range. next_page stops at the last page, prev_page stops at 0, and a page index past the end is clamped when the query runs. Filtering a thousand rows down to three cannot leave you stranded on an empty page 40.
Paging intents
use grid_state::GridState;

let mut s = GridState::new(10, false);
s.next_page(3);              // 0 → 1; needs the page count to clamp
s.next_page(3);              // 1 → 2
s.next_page(3);              // last page → no-op
assert_eq!(s.page(), 2);
s.prev_page();
assert_eq!(s.page(), 1);

s.set_page_size(50);         // → page 0
assert_eq!(s.page(), 0);

next_page takes the page count because GridState holds no data and cannot know how many pages exist — the count comes from the latest GridPage. That is the same separation that lets the state machine be unit tested without any rows at all.

Selection is untouched by paging. Neither turning a page nor changing the page size clears it, so a cross-page selection is safe to build up before acting on it.

#Large pages

Above roughly sixty rows on a page, the list view renders only the visible window plus an overscan, padded top and bottom with spacers. Below that threshold every row renders with natural height and no fixed sizing — the common case pays nothing.

Virtualization needs uniform row heights, so it applies only to the plain columnar table. Card view, grouped view and a custom row slot render flat. If you use "100 / page" with a custom row renderer, expect the full hundred in the DOM.

Pagination is not just a UI convenience. It is the mechanism that keeps the DOM small. For datasets past what a browser should hold at all, move the query server-side with on_query — see server-side querying.

#View mode

The toolbar toggles between the row list and a card gallery. ViewMode lives in GridState alongside the query, so switching views keeps your search, filters, sort, page and selection exactly as they were.

PropEffect
grid_default: trueStart in card view.
no_card_toggle: trueHide the toggle and stay in list view.
cardCustom card body. When None, one is built from the columns.
density: GridDensity::MinimalStrips the filter funnels, column chooser and group-by, and hides the footer when everything fits one page.

Use no_card_toggle for inherently tabular data — a permission matrix, a ledger — where a gallery view carries no meaning and the toggle is just noise. Use Minimal density for small, glanceable sets: sort, selection, search and export still work, but the enterprise chrome is gone.
